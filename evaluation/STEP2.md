## 2. 为什么采用“标注原文证据覆盖”

第一阶段的gold_evidence是几段已核对的原文摘录，并没有穷尽标注知识库中所有语义相关片段。因此，现阶段不能声称自己已经拥有传统片段级Recall@k需要的完整相关性标签。

本轮采用一个定义清楚、可以完全离线复核的规则：**检索结果是否覆盖了指定文件、指定位置的完整原文摘录。**

这个规则有意保守：

1. 其他章节出现了同样的事实，也不会自动算作命中了指定的原文位置。
2. 只覆盖摘录的一部分，即使那一部分可能已经足以回答问题，也不算完整覆盖该摘录。
3. 相似度再高，只要没有覆盖目标原文，也不会因此得分。
4. 不用模型判断语义，所以不会假装程序已经理解了所有等价表述。

本轮数值适合说明“标注依据有没有被检索出来”。以后加入最小事实证据和等价证据标注后，才能进一步评价更广泛的语义相关性。

## 3. 为什么需要区间并集，不能只检查quote是否出现在一个片段里

位置采用Python常见的左闭右开写法。例如 `[10, 20)` 表示从第10个字符起，到第20个字符之前结束，总长度是 `20 - 10 = 10`。

假设一条证据在 `[10, 20)`，返回片段依次覆盖：

```text
排名1：[10, 16)
排名2：[14, 20)
```

第一条覆盖6个字符；两条一起覆盖10个字符，而不是 `6 + 6 = 12` 个字符，因为 `[14, 16)` 被重复覆盖了。

如果实际返回的是：

```text
排名1：[10, 14)
排名2：[15, 20)
```

中间 `[14, 15)` 仍有缺口，所以只有9个字符被覆盖，不能判为整条证据完成。不同文件或不同PDF页码的区间，也不能拼在一起。

你的题库里就有真实的跨片段情况：eval_003的第一条标准证据位于C3的 `[18710, 18842)`。按当前300字符、重叠50字符切分，它跨越 `[18500, 18800)` 和 `[18750, 19050)`。如果两段都被检索出来，程序应该允许它们共同覆盖证据，而不能要求每个片段单独包含整个quote。

本次运行实际没有检索到这两段；这里解释的是为什么评分算法必须正确处理这种情况，不是在把一个未发生的命中计入成绩。

## 4. 每个指标怎样计算

设一道题有m条标注证据；前k个检索片段完整覆盖了其中c条。只有来源、页码相同，并且区间并集覆盖整条摘录，才算“完整覆盖”。

| 返回字段 | 指标名 | 单题计算方法 |
| --- | --- | --- |
| evidence_hit_at_1 | EvidenceHit@1 | 只看第一条结果，至少完成一条证据记1，否则记0 |
| evidence_hit_at_k | EvidenceHit@k | 前k条合起来至少完成一条证据记1，否则记0 |
| evidence_recall_at_k | EvidenceRecall@k | 完成的标注证据条数c，除以全部标注证据条数m |
| evidence_rr_at_k | EvidenceRR@k | 最早完成任一条证据的结果前缀长度为r时，记1/r；前k条仍没完成则记0 |
| all_evidence_at_k | AllEvidence@k | 前k条完整覆盖全部标注证据记1，否则记0 |

这里的EvidenceRecall不是传统chunk Recall：它的分母是**本题标注的原文摘录数**，不是知识库中所有相关片段的数量。

EvidenceRR也不是传统MRR所使用的“第一条相关单片段排名倒数”：它允许前两条或前三条结果共同完成一条证据。我们把它明确称为“证据完成倒数排名”；按题求平均后是“平均证据完成倒数排名”，不把它冒称为标准MRR。

上面的两段拼接例子中：

```text
EvidenceHit@1 = 0       第一条只覆盖6/10字符
EvidenceHit@3 = 1       前两条已经共同完成证据
EvidenceRecall@3 = 1/1 = 1
EvidenceRR@3 = 1/2 = 0.5
AllEvidence@3 = 1       唯一一条证据已经完成
```

除了汇总分数，还保存三个诊断字段：

| 字段 | 作用 |
| --- | --- |
| covered_evidence | 与gold_evidence顺序一致的布尔列表，例如 `[true, false]` 表示第一条完整、第二条未完整 |
| first_completion_rank | 首次完成任一条证据的前缀排名；没有完成时为null |
| character_coverage | 每条摘录被覆盖的字符比例，用于观察缺口；不是事实正确率或语义完整性 |

资料不足题没有正向证据，m为0，不能计算这个召回比例。因此，它的五项指标都是null，诊断列表为空。null表示“不适用”，不是0分，也不是系统已经成功拒答。

## 6. 汇总分数为什么是这些数字

先逐题评分，再对4道有正向证据的题求平均。这叫按题宏平均：每道题权重相同，不因某题有两条证据就让它权重翻倍。

```text
平均EvidenceHit@1
= (0 + 0 + 0 + 0) / 4
= 0

平均EvidenceHit@3
= (0 + 0 + 0 + 1) / 4
= 0.25，即25%

平均EvidenceRecall@3
= (0/1 + 0/1 + 0/2 + 1/1) / 4
= 0.25，即25%

平均EvidenceRR@3
= (0 + 0 + 0 + 1/2) / 4
= 0.125

平均AllEvidence@3
= (0 + 0 + 0 + 1) / 4
= 0.25，即25%
```

不是除以5，因为第五题没有正向证据。也不是把总共找齐的1条证据直接除以所有5条标注证据；后者得到20%，属于另一种加权口径，不是本报告采用的按题宏平均。

本轮没有检索异常。代码仍保留了失败处理约定：单题检索失败会保留错误，有答案题按0计入均值，避免删掉失败样本抬高分数；若原文版本或入库完整性等预检失败，则整轮不产生评分。

新增脚本的可执行语句上方已逐行添加中文注释，函数开头也有总体说明。建议按下面顺序读，先理解主流程，再进入细节：

1. `run_retrieval.py`底部的 `if __name__ == "__main__"`：只有直接运行脚本才执行main，导入函数不会启动评估。
2. `main()`：从参数解析开始，串起各个函数。暂时把每个被调用函数当成一个有明确输入、输出的小工具。
3. `load_dataset()`：读取JSON，核对SHA-256，根据行号和quote定位字符起止位置。
4. `audit_collection()`：核对题库对应原文是否完整入库，逐段比较文本与原文切片，避免拿旧资料评分。
5. `search_index()`的调用位置：确认检索只收到本轮question、集合名称和top_k，没有收到参考答案或历史。
6. `attach_positions()`：原检索结果没有start/end，按ID补回这些元数据；用字典对应ID，保留query的原始排序。
7. `interval_coverage()`：先看上面的10字符例子，再逐行读排序、裁剪、去重的计算。
8. `score_retrieval()`：依次检查前1、前2、前3条的覆盖状态，计算首次完成排名以及最终指标。
9. `summarize()`：排除无答案题，逐题宏平均，保留异常数量和耗时口径。
10. `markdown_report()`及写盘代码：同一个report对象生成JSON和Markdown，保证数值对应。

其中最核心的一行是：

```python
references, _ = search_index(case["question"], name, args.top_k)
```

`case["question"]`取出本题问题；`name`是已经固定的集合；`args.top_k`是返回数量；`references`接收有序检索结果；下划线接收但不使用第二个返回值，即该集合总片段数。题库中的标准答案没有作为调用参数传入。

另一个关键计算是：

```python
sum(covered_evidence) / len(evidences)
```

`covered_evidence`是布尔列表；Python求和时True按1、False按0计算。因此，分子是完整证据条数，分母是本题全部标准证据条数。无证据时已在函数前部返回None，不会执行除零。

| dataset_path、dataset_sha256、dataset_version | 固定题库文件及其版本 |
| collection、collection_metadata、collection_configuration | 固定所用集合、模型及距离配置 |
| collection_count、audited_chunk_count | 区分全库规模和题库来源的核查规模 |
| query_policy | 明确记录只用当前问题、无来源过滤、不输入标准答案 |
| warmup_seconds | 本机模型加载与首次向量化耗时 |
| cases | 每题的输入、标注、检索结果、指标、状态及耗时 |
| mapped_evidence | 标准证据及换算后的start/end字符位置 |
| overlapping_chunk_ids | 与原文证据有字符交集的片段ID，帮助定位；不代表每段都足够回答，也不是全部语义相关片段的标签 |
| references | 本次真正返回的Top-k片段，保留原排序、正文、来源、相似度和位置 |
| summary | 四道正向题的宏平均及运行完成数、耗时中位数 |
| status、error | 保存正常、部分失败或预检失败状态及原因 |

`ok`表示这一题的检索和评分程序正常完成，不表示这道题得了满分。JSON里的相似度是检索排序用的向量相似度，不是问题回答正确的概率。

## 12. 本阶段的边界与下一步

本轮建立的是可复查的初始基线。5题太少，而且正向标注仅有4题，某一道题变化就会让命中率改变25个百分点。不要把这组数值当作整个项目、所有资料或所有用户问题的稳定质量结论。

目前可以确定：脚本在固定集合上完整跑完；资料版本核对通过；当前Top-3检索没有覆盖前3道题指定的原文锚点，第4题在第二名完成锚点覆盖。它还不能告诉我们DeepSeek最终会答成什么样。

下一步应先复核这些逐题结果，讨论是否需要补充最小事实证据和等价依据，再设计改动检索方式的对照实验。本阶段没有自动提高Top-k、改写问题、增加重排器或修改向量模型，以便保留可以比较的原始结果。
