# 第一阶段：5道示范评估题

`demo_questions.json` 保存评估输入、参考答案、必要事实和原文依据。本文件保留第一阶段的题库与字段说明。第二阶段的离线检索脚本已实现并运行，详见 [STEP2.md](STEP2.md)；尚未执行DeepSeek回答评测。

题目选自现有 `资料/docs/C3/C3.md`（第三章）和 `资料/docs/C5/C5.md`（第五章）。本版由助手依据原文逐条核对，供你复核；引用均保持原文，包括原文中的空格。这里只评估指定教材内容，不把旧教材中的路径、参数或API示例当成当前应用配置。

## 文件与存放位置

```text
application-llm-universe/
├── evaluation/
│   ├── demo_questions.json   # 机器可读取的题库
│   ├── README.md             # 第一阶段字段说明
│   ├── run_retrieval.py      # 第二阶段离线评估入口
│   ├── retrieval_metrics.py  # 原文区间覆盖与指标计算
│   ├── STEP2.md              # 第二阶段运行、代码与结果讲解
│   └── runs/                # 每次运行的JSON和Markdown报告（本地保存）
├── 资料/docs/C3/C3.md        # 第三章原文
├── 资料/docs/C5/C5.md        # 第五章原文
├── Histor/                  # 日常对话历史，与评估题库分开
└── .local/chroma/            # 已有向量数据库，本阶段没有改动
```

不要把整个evaluation文件夹复制或上传进“资料”。标准答案属于评分材料；把它入库后再检索，相当于把答案直接放进考试材料，会失去评估原资料检索能力的意义。

## 5道题分别练习什么

| 题号 | 类型 | 核心问题 | 参考答案要点 |
| --- | --- | --- | --- |
| eval_001 | 直接事实题 | C3 3.3.4示例的两个切分参数是多少？ | CHUNK_SIZE=500，OVERLAP_SIZE=50 |
| eval_002 | 同义改写题 | 相邻小段为什么保留重复文字，由什么参数控制？ | 保持上下文连贯、避免丢失上下文；chunk_overlap |
| eval_003 | 多段证据题 | 为什么切分长文档，优化后重新验证什么、为什么？ | 上下文长度限制；验证全部案例；避免原有好案例退化 |
| eval_004 | 多轮追问题 | 根据固定历史，“它”的持久化路径是什么？ | 教材示例中的../../data_base/vector_db/chroma |
| eval_005 | 资料不足题 | C3有没有报告独立测试集上的Recall@3实测值？ | 未报告，不能编造百分比 |

eval_001中的500不是当前应用默认的300；eval_004中的路径不是当前应用的.local/chroma。限定“教程示例”能让评分标准明确。

eval_002用“重复文字”表达原文的“共享字符”，用于观察同义表达。它与eval_001在主题上相关，这5题属于教学开发集；以后划分开发集和独立测试集时，不要把等价事实的同义题分到两边。

eval_003必须结合两份文件：C3解释切分原因，C5说明优化后的验证原则。这里要求的推理是把一般优化原则应用到调整切分策略，并不是原文存在一个与题目逐字相同的问答。

eval_004的history固定了“该节”和“它”的指代，历史本身没有提供本轮问题的答案。当前项目检索只使用本轮问题，而生成阶段会收到历史；以后可以用此题观察这两部分的差异。

eval_005是有意保留的反例：教材出现k=3，并不代表给出了Recall@3。没有给出相关片段的人工标注和评估结果，不能从返回数量推算召回率。该题只限定第三章；不把其他文档是否包含类似数字作为标注依据。

## 最外层字段

整个JSON是一个对象，里面的cases列表才是5道题。以后Python读取时可用 `dataset["cases"]` 取得题目列表。

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| version | 整数 | 题库版本；当前为1。修改题目或评分规则后应记录新版本，避免混比成绩。 |
| description | 字符串 | 说明题库的目的和范围，不是发送给回答模型的提示词。 |
| source_root | 字符串 | 原文根目录，相对于demo_questions.json所在文件夹解析；../资料表示返回项目根目录后进入资料文件夹，不依赖终端当前目录。 |
| source_versions | 对象列表 | 记录本次核对过的原文件及其SHA-256内容摘要，便于发现原文之后是否改变。不是Chroma集合列表，也不是整个资料文件夹的清单。 |
| cases | 对象列表 | 实际题目；本版恰好5条。 |

source_versions中的每项包含：

| 字段 | 作用 |
| --- | --- |
| source | 相对于source_root的原文路径，例如docs/C3/C3.md。 |
| sha256 | 原文件字节内容的摘要。原文件改变后需重新核对标注，不能只更新摘要而不检查答案。摘要不是向量、不是密钥，也不证明标注在语义上正确。 |

路径的组合方式是：`题库所在文件夹 / source_root / source`。例如第一道题的原文最终位于 `application-llm-universe/资料/docs/C3/C3.md`。

## 每道题的字段

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| id | 字符串 | 唯一题号，用来把同一道题在不同运行中的结果对齐。它不是Chroma片段ID。 |
| category | 字符串 | 题型；以后可以按题型统计表现，避免总分掩盖某类问题。 |
| question | 字符串 | 本轮实际问题。不要把reference_answer拼进它。 |
| history | 消息列表 | 本轮之前的固定对话；单轮题为空列表。消息按实际时间顺序排列，本轮question不重复放入history。 |
| source_scope | 路径列表 | 题目要求依据哪些教材作答，也是标注时的核查范围。它本身不会修改现有检索函数或自动过滤Chroma；其他文档仍可能作为干扰被检索。 |
| answerable | 布尔值 | 指定范围的原文是否提供足够依据回答目标问题，与系统本次有没有检索成功不同。true表示有，false表示没有。 |
| expected_behavior | 字符串 | answer表示应根据资料回答；abstain表示应说明资料不足、不能编造目标信息。 |
| reference_answer | 字符串 | 经过原文核对的参考表述，不是系统已经生成的答案。允许等价措辞，不要求逐字匹配。 |
| required_facts | 字符串列表 | 正向回答必须覆盖的事实要点，用来逐项检查遗漏。本版资料不足题为空，不通过“必须猜出一个数值”评分。 |
| gold_evidence | 证据对象列表 | 支持参考答案的原文摘录与位置。gold表示用作评分标准的依据，本版由助手核对、供你复核，不是实际检索结果。 |
| annotation_notes | 字符串 | 给标注者和后续评分程序的解释，包括易错点、推理关系和缺失信息的核查过程；不作为回答模型的输入。 |

JSON中的true、false、null分别对应Python中的True、False、None；JSON不能直接写Python的#注释。因此，字段解释放在本README里，单题补充说明放在annotation_notes中。

### history里的消息

| 字段 | 作用 |
| --- | --- |
| role | user表示用户说的话，assistant表示助手此前的回复。 |
| content | 这一条历史消息的文本。 |

eval_004应按“历史中的user → 历史中的assistant → 本轮question”的顺序输入。不能混入其他题的聊天。当前prepare_rag_messages函数要求conversation最后一条就是本轮用户问题，因此后续评估脚本会复制history，再追加本轮question；本阶段只是记录数据。

### gold_evidence里的字段

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| source | 字符串 | 相对于source_root的文件路径，与项目中资料来源的命名方式一致。 |
| page | 整数或null | PDF物理页码约定从1开始；本版全部来自Markdown，所以为null，不能写成0或虚构页码。 |
| line_start | 整数 | 摘录所在的Markdown原文件起始行，从1计数。 |
| line_end | 整数 | 摘录所在的结束行，包含这一行；与line_start相同表示在同一行内。 |
| quote | 字符串 | 逐字摘录的原文，可以是所在行的一部分，不必复制整行。多行用JSON的\n保存，读取后还原成真正换行。 |

行号是Markdown编辑器中的行号，不是PDF页码、字符偏移或Chroma片段编号。本版只为Markdown设计了行号标注；以后加入PDF时，需要按页提取原文并重新约定定位方式。

原文证据与向量库片段也不是同一种东西：一条quote可能跨越当前切分边界，同一个事实也可能出现在多个重叠片段中。本版gold_evidence是足以支持答案的证据摘录，不是对知识库里所有相关片段的穷尽标注。因此，不能直接把证据项数当成chunk级Recall@k的分母，也不能将未列出的等价证据自动判错。

题库本身没有绑定Chroma集合，也没有穷尽标注gold_chunk_ids。第二阶段脚本会在每次报告中固定集合、核对原文版本，并将证据定位为字符区间，计算严格的标注原文覆盖指标；跨集合不能只用chunk-000001这样的顺序ID识别资料。原文有答案但解析失败或未入库，应报告处理或入库问题，不应偷偷把answerable改为false。

## 先人工练习，再写评估程序

1. 从eval_001开始，打开source对应文件，按行号找到quote。
2. 核对reference_answer的每个必要事实是否确实得到原文支持。
3. 按同样方法读eval_002和eval_003，理解同义表达和多条证据。
4. 按固定history读eval_004，确认“它”指向哪个对象。
5. 阅读eval_005的核查说明，理解资料不足时为什么不能伪造证据或百分比。

资料不足题的gold_evidence为空，因为找不到支持目标数值的正向依据；不是因为漏填。required_facts也为空，但expected_behavior与annotation_notes给出了判分标准。这类题不纳入相关片段Recall的分母，后续单独评价是否合理说明不足。

正常评测只把question和规定的history交给现有问答流程。reference_answer、required_facts、gold_evidence和annotation_notes留给评分使用；source_scope通过题目及历史中的表述限定回答范围，不直接注入答案。

这5题已经过原文核对，但仍只是教学开发集，不代表全面覆盖所有文档、问题类型或用户场景。第二阶段仍复用原网页的检索逻辑，没有修改网页、知识库、历史记录或模型参数。阅读完本文件后，可以按STEP2.md学习离线脚本和实际结果；生成回答的评估属于后续阶段。
